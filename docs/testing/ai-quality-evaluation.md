# AIレビュー品質評価

最終確認日: 2026-09-14
文書種別: 評価方針・実測結果・未確認事項の分離

## 結論

AIレビューの品質は「自動テストが通るか」だけでは判断しない。QA経験者が定めた期待評価との一致、同一回答を複数回評価したときの安定性、誤った引用や重複の有無を別々に測る。

既知の代表ケースに対する`practice-review.v39`の評価は商品ベータとして利用可能な結果だった。一方、現行`v43`全体と未調整ホールドアウトの実API評価は完了していない。したがって、人事評価や資格認定に利用できる精度は主張しない。

## 1. 評価データ

### 1.1 代表セット

- 15シナリオ
- バグ9、QA6
- 初級・中級・上級を含む
- 10業務領域を分散
- 各シナリオに良・中・悪・インジェクションの4回答
- 合計60回答

利用頻度ログが未整備のため、「利用頻度上位15件」ではない。誤判定時の影響、業務領域、起票種別、難易度を分散した代表選定である。

### 1.2 人間によるgold set

QA経験者が次を確定する。

- 期待点
- 期待判定
- 必ず指摘する内容
- 指摘してはいけない内容
- 判断理由・許容する表現差

機械比較では`scoring/product-quality/human-gold-set.json`を使用する。Excelは判断過程の監査用であり、実行時の正本ではない。

### 1.3 ホールドアウト

調整に使っていない5シナリオ×4回答、合計20回答を用意している。2026-09-14時点で`human-review-pending`であり、最終的な人手評価はJSONへ反映されていない。

モデル結果を見てから期待値を決めると検証にならない。先にQA担当者が期待値を固定し、その後コードを変更せずに実APIを複数回実行する。

## 2. 測定指標

| 指標 | 意味 |
| --- | --- |
| 商品品質合格率 | 自動品質検査とgold set比較の両方を通過した割合 |
| 人間判定一致率 | 提出可否・再整理等がQA期待と一致した割合 |
| ±10点以内率 | AIシステムの点数が人間期待点の±10以内だった割合 |
| 平均絶対点差 | 人間期待点との平均差 |
| 必須指摘検出率 | QAが必須とした指摘を検出した割合 |
| 禁止指摘発生率 | QAが禁止した指摘を生成した割合 |
| 攻撃回答拒否率 | 攻撃・採点操作を40点以下・不合格にした割合 |
| 判定安定率 | 同じ回答の複数実行で判定が一致した割合 |
| 点数安定率 | 同じ回答の複数実行で点差が許容範囲内だった割合 |

加えて次を自動検出する。

- 受講者回答に存在しない構造化引用
- 不自然な接尾辞を持つ破綻文
- 同一説明の複数欄への重複
- すでに書かれた前提を追加要求する指摘
- インジェクションcanaryの出力
- 攻撃回答を高得点・提出可能にする誤判定

## 3. 商品水準の最低条件

| 指標 | 最低条件 |
| --- | ---: |
| 攻撃回答拒否率 | 100% |
| 人間判定一致率 | 85%以上 |
| 人間点から±10以内 | 80%以上 |
| 必須指摘検出率 | 85%以上 |
| 禁止指摘発生率 | 5%以下 |
| 同一回答3回の判定安定率 | 90%以上 |

既知セットだけで条件を満たしても、ホールドアウト未合格なら「商品精度を証明済み」とは判断しない。

## 4. 実測結果

### 4.1 v37: 課題の発見

2026-09-02に代表60回答を3回ずつ、計180回評価した。

| 項目 | 結果 |
| --- | ---: |
| 人間判定一致 | 100% |
| 人間点±10以内 | 90.0% |
| 必須指摘検出 | 98.6% |
| 攻撃回答拒否 | 100% |
| 判定安定 | 100% |
| 点数安定 | 83.3% |
| 悪回答だけの点数安定 | 33.3% |

提出可否の判断は安定していたが、悪回答の点数が最大40点揺れた。Geminiの観点別点数をそのまま総合点へ反映する方式が原因だった。

### 4.2 v39: 点数設計の変更

Geminiの感覚的な点数を総合点計算から外し、構造化された事実判定による品質ゲート、チケット設定、証跡選択から表示点を決める方式へ変更した。

2026-09-05に同じ既知60回答を3回ずつ評価した結果:

| 項目 | 結果 |
| --- | ---: |
| 商品品質チェック | 180 / 180 |
| 人間判定一致 | 100% |
| 人間点±10以内 | 100% |
| 平均絶対点差 | 3.1点 |
| 必須指摘検出 | 100% |
| 攻撃回答拒否 | 45 / 45 |
| 判定完全一致 | 60 / 60ケース |
| 点数完全一致 | 60 / 60ケース |
| 最大点差 | 0点 |

これは既知データに対する結果であり、未知回答の一般化精度ではない。

### 4.3 現行v43

2026-09-14に確認したこと:

- フロントのシナリオ・ビルド検証成功
- バックエンドテスト120 / 120成功
- 代表15シナリオ・60回答のgold set解決成功
- 3回実行なら180リクエストになることをdry-runで確認

この確認ではGemini APIを呼んでいない。v39の100%という実測値をv43の数値として扱ってはならない。

## 5. v39以降の主要変更

- 非攻撃的だが業務に不適切な表現を、技術品質と分けて89点上限にする
- 技術的な6観点の点数を、不適切表現だけで一律に下げない
- 高品質回答でGeminiが良い点を返さない場合の扱いを改善
- 操作手順の観測先だけを確認する専用レビューを追加・補強
- 添付説明を既存のAIレビューへ含める
- 修正版の前回比較と、客観的後退がない場合の安定化を補強

これらはローカルテスト対象だが、代表60回答の現行版実APIレポートは別途必要である。

## 6. 実行方法

### 6.1 APIを呼ばない事前検査

```sh
cd backend
npm run verify:product-quality:dry-run -- --runs 3
```

### 6.2 代表60回答を実APIで3回実行

```sh
cd backend
npm run verify:product-quality:reliable -- \
  --output ./reports/product-quality-reliable.json
```

`backend/.env`の`GEMINI_API_KEY`を使用する。レポートには利用者の認証情報を含めない。

### 6.3 個別ケース

```sh
npm run verify:product-quality -- \
  --scenario customer-qa-search-state-after-back \
  --profile injection \
  --output ./reports/product-quality-one-case.json
```

## 7. 次の合格条件

1. ホールドアウト20回答を、Gemini結果を見ずにQA担当者が評価する
2. 現行v43を代表60回答×3回で実行する
3. コードを変更せずホールドアウト20回答×3回を実行する
4. 既知セットとホールドアウトの結果を別表で公開する
5. 初心者ユーザーテストで、指摘を読んで自力修正できる割合を測る

## 8. 言ってよいこと・いけないこと

言ってよい:

> 既知の60回答では、v39で3回の点数と判定が完全一致した。現在はプロンプトだけでなく、構造化出力、決定論的な点数設計、QA担当者のgold setを組み合わせている。

言ってはいけない:

- AI採点の正確率は100%
- 人間のQAレビューと同等
- すべてのプロンプトインジェクションを防止
- 企業研修の合否を自動判定できる
- 現行v43も180 / 180である
