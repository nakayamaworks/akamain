# バグ起票トレーニング 作成モード設計

## 文書情報

- ステータス：フェーズ3Aパイロット稼働中（認証付きGemini採点は1シナリオで接続済み）
- 対象：`typing_workbench`
- 目的：タイピング中心の初期体験から、自分でバグ報告を書く体験へ発展させる
- 注意：本書は設計を整理するものであり、未決定事項を実装仕様として確定しない

### 実装済み

- チケット一覧では「チケット作成」からバグシナリオ画面へ進む
- バグシナリオ画面の「見本入力を開始」「実践起票を開始」で作成モードを決める
- バグシナリオ画面では、開始ボタンをPC画面下部の固定アクションフッターへ常時表示する
- 独立したモード切替パネルは設けない
- 選択した作成モードを端末内へ保存する
- 実践起票で題名とテンプレート各欄を自由入力する
- 未入力項目を文章入力完了前に確認する
- 説明欄直下には「チケット情報の設定へ」ボタンだけを置き、未入力時だけ不足項目を表示する
- チケット情報の設定中も題名と説明を直接修正できる
- 見本入力の結果から同じ題材の実践起票へ進む
- 実践起票後に自分の回答と見本回答を比較する
- 全シナリオへ永続的なシナリオIDを付与する
- 顧客重複登録シナリオの採点基準と5種類のテスト回答を定義する
- 受験履歴と構造化採点結果の保存形式を定義する
- Gemini接続前の固定サンプルで採点結果画面を確認できる
- 全27シナリオに、見本回答から独立した現場メモを定義する
- 現場メモは複数の報告・確認結果・仕様情報へ事実を分散し、完成した題名や詳細を表示しない
- シナリオ単位で確認環境を指定し、本文・担当領域・添付証跡と一致させる
- シナリオ追加時に現場メモの定義漏れや見本回答の露出を自動検証する
- チケット一覧と練習シナリオを分離し、開始前の一覧には正解の題名・優先度・担当者を表示しない
- 実践起票の完了後は、利用者自身が作成・選択した内容を試作チケットとして一覧へ追加する
- マイページでは未挑戦シナリオの題名を伏せる
- Googleログイン、Cloud Run経由のGemini採点、Sheetsへの履歴保存
- マイページの履歴、ステータス、ランキング表示

### 未実装

- 顧客重複登録以外のシナリオに対するAI文章採点
- 未経験題材だけを対象にした腕試し
- 項目ごとの書き出し補助、要点補助

## 1. 背景

現在のトレーニングでは、題名と説明の完成文が用意されており、利用者は表示された文章をタイピングする。

この方式は、バグ起票の構成や表現を覚える用途には適している。一方で、実務に必要な「未整理の情報から題名と説明を組み立てる力」は訓練できない。

次の段階では、説明欄の構成をシステム側で用意しつつ、題名と各セクションの文章を利用者自身が作成する。

## 2. 難易度を表す2つの軸

プロジェクトの業務領域と、文章作成の難易度は別の軸として扱う。

### 2.1 業務領域

`rmProjectSwitcher` では、難易度ではなく業務領域として分類する。

#### 一般業務

- 顧客管理システム
- 勤怠管理システム
- 美容室予約システム

#### 商取引・業務運用

- ECサイト
- 在庫管理システム
- スマホアプリ

#### 高信頼性・専門領域

- 車載ソフト
- 決済システム
- 医療システム

この分類はドメインの性質を表すものであり、文章作成レベルの初級・中級・上級を意味しない。

### 2.2 作成モード

利用者に表示する作成モードは、当面次の2つとする。

#### 見本入力

プロジェクト所定のテンプレートへ入力済みの完成例を表示し、利用者がそのままタイピングする。

主な目的：

- バグ報告の基本構成を覚える
- 題名や説明の表現例を知る
- タイピングの速度と正確性を高める

#### 実践起票

題名は空欄とし、説明欄にはプロジェクト所定のテンプレートを表示する。利用者は提示された調査情報を基に、題名と各セクションの本文を作成する。

主な目的：

- 未整理の事実を文章へ変換する
- 事実を適切なセクションへ配置する
- 期待結果と実際の動作を分離する
- 推測を事実として断定しない文章を書く

「実践」は、見本を写すのではなく、自分の判断で文章を作ることを表す。「起票」は、単なる文章入力ではなく、業務上のチケットを作成することを表す。

## 3. 実践起票の基本構成

### 3.1 題名

初期状態は空欄とする。

利用者は、対象・操作または条件・発生した現象が伝わる題名を作成する。

題名の例：

```text
保存ボタンを連続クリックすると顧客データが重複登録される
```

### 3.2 説明

説明欄には、選択中のプロジェクトで定められたテンプレートを表示する。

次のセクションは現在の代表例とする。

```text
■詳細

■前提条件

■操作手順

■期待結果

■備考

■実際の動作

■再現性
```

テンプレートは学習用のガイドではなく、プロジェクトの運用ルールである。見本入力と実践起票で共通して使用し、作成モードによってテンプレート自体を変えない。

プロジェクトごとにセクション構成が異なる場合は、そのプロジェクトのテンプレートを表示する。

見出しの削除可否や並べ替え可否は未決定とする。最初の実装では、プロジェクト所定の構成として固定する案を優先する。

### 3.3 入力材料

画面右側には、文章化される前の調査情報を表示する。

表示候補：

- 現場から届いた報告
- 発生日時
- 確認バージョン
- OS、ブラウザ、端末などの環境
- 発生条件
- 操作内容
- 実際に確認された結果
- 仕様書や期待動作
- 再現回数
- 影響範囲
- 回避策
- 関係者
- 対応日程
- 関係のない補足情報

すべての情報をチケットへ書くことが正解とは限らない。必要な情報を選ぶ行為もトレーニング対象とする。

## 4. 画面上の進行

### 4.1 開始前

利用者は次の項目を選択する。

1. プロジェクト
2. 「見本入力を開始」または「実践起票を開始」

作成モードが増えても、業務領域の分類とは混在させない。
チケット一覧では作成モードを選ばず、「チケット作成」からバグシナリオ画面へ進む。シナリオを確認した後に「見本入力を開始」または「実践起票を開始」を選び、同じ判断を二度求めない。

グローバルメニューには実際に利用できる「ホーム」「マイページ」だけを表示する。プロジェクト画面ではプロジェクト名、プロジェクト切り替え、チケット作成、チケット一覧を表示し、未実装のRedmine機能をダミータブとして並べない。マイページ内の「学習状況」「履歴」「ランキング」はすべて実機能として表示する。存在しない機能を無効ボタンで表現せず、実装された時点でナビゲーションへ追加する。

チケット一覧へ練習シナリオの見本回答を並べない。一覧には練習対象外の既存チケットと、利用者が実践起票で作成したチケットを表示する。「チケット作成」を押したときだけ、画面に出ていないシナリオプールから次の未整理報告を自動選択する。未挑戦が残っている場合は未挑戦を優先し、すべて挑戦済みの場合は最高点が低いもの、次に最終挑戦日時が古いものを復習候補にする。見本入力の完成文は一覧へ追加しない。

未挑戦シナリオは題名を伏せるため、番号による個別選択をさせない。マイページではプロジェクト単位の「新しいシナリオに挑戦」から自動選択する。挑戦済みシナリオだけ題名を開示し、「再挑戦」から同じ題材を明示的に選べる。

実践起票は検証済みFirebase UIDのAttemptとして保存し、チケット一覧は永続化された本人の履歴から復元する。固定のダミーチケットは表示しない。利用開始時に匿名アカウントを自動発行するため、Googleログインなしでも実践起票を開始できる。

チケット一覧の題名は`#/tickets/{attempt_id}`へのリンクとし、起票確認画面では選択したチケット設定、説明、添付エビデンス、AIレビューを読み取り専用で表示する。マイページの履歴も同じ起票確認画面へ遷移し、詳細表示を二重実装しない。

実践起票の結果画面には「同じシナリオに再挑戦」と「次の未挑戦シナリオへ」を表示する。現在のプロジェクトに未挑戦がない場合、後者を「別のシナリオを復習」に切り替える。マイページの学習状況には最高点、直近得点、挑戦回数を分けて表示し、履歴自体は上書きしない。

バグシナリオ画面では、スクロール位置にかかわらず画面下部へ固定アクションフッターを表示する。左側に「一覧へ戻る」、右側に2つの開始ボタンを配置し、本文にはフッターで隠れないだけの下余白を確保する。スクロール方向による自動表示・非表示は行わない。スマートフォンでの利用は非推奨とし、この導線はPC向けに設計する。

### 4.2 作成中

実践起票では、次の状態を基本とする。

- 題名は通常のテキスト入力
- 各セクション本文も通常のテキスト入力
- ローマ字ガイドや正解文字の逐次表示は行わない
- 入力材料は作成中いつでも確認できる
- 一時保存または入力内容の保持を検討する
- AI採点前に利用者自身で読み直せる
- 説明欄直下の「チケット情報の設定へ」を押すと障害レベルへフォーカスする。通常時は説明文を表示せず、未入力時だけ不足項目を表示する
- 次の工程へ進んだ後も文章はロックせず、再編集モードを設けない
- 最終的な「作成」でも文章の未入力項目を再確認する

### 4.3 提出前

AIへ送信する前に、機械的に確認できる不足を表示する。

確認例：

- 題名が空欄
- 必須セクションが空欄
- 操作手順が存在しない
- 再現性が未入力
- 入力文字数が極端に少ない

この確認は文章の良し悪しを採点するものではない。

### 4.4 採点後

AIを単なる点数付けには使わず、開発・QAが不具合票を受け取ったときの読み手視点を表示する。

表示順：

- AIレビューを結果画面の主コンテンツとして最上段へ置く
- 総合評価と6軸レーダーを表示する
- 読み手が疑問に思う点を、不足情報と調査提案に分ける
- 誤解される可能性がある表現を引用して説明する
- 次に行う確認・切り分けを、目的とともに表示する
- 改善効果がある場合だけ書き換え例を表示する
- チケット設定と添付証跡の機械判定はAIレビューの後へ置く
- 参考回答は初期表示せず、「見本回答を確認する」で任意表示する

参考回答は唯一の正解として扱わない。

### 4.5 同じ題材で学ぶ

見本入力と実践起票は、同じシナリオデータを利用できるようにする。

学習目的では、次の順番を基本とする。

1. 見本入力で完成例と起票の型を確認する
2. 「この題材で実践する」を選ぶ
3. 同じシナリオの見本回答を隠す
4. 調査情報とプロジェクト所定のテンプレートから実践起票する
5. 自分の回答、AIの評価、見本回答を比較する

同じ題材を使う目的は、見本で確認した考え方を自分で再構成することにある。単なる暗記にならないように、実践起票中は見本回答を表示しない。

### 4.6 未経験題材で腕試しする

実力確認では、見本入力で事前に回答を見ていないシナリオを使用する。

腕試しの条件：

- 未経験または最近見本を確認していない題材を選ぶ
- 実践起票から開始する
- 見本回答は採点後に表示する
- AI採点では文章表現の一致ではなく、事実・構成・再現性を評価する

最初の開発では同じ題材を使う学習導線を優先する。シナリオ数が増えた段階で、未経験題材による腕試しを追加する。

## 5. 支援レベルの内部設計

### 5.1 シナリオデータの共通化

見本入力用と実践起票用にシナリオを複製しない。1つのシナリオに、両モードで使用する情報をまとめる。

想定する共通データ：

```js
{
  scenarioId: "",
  projectId: "",
  templateId: "",
  fieldReport: {
    notes: [],
    environment: []
  },
  writingExample: {},
  reviewSource: {},
  scoringRubric: {}
}
```

モードごとの利用方法：

- 記載例入力は `writingExample` を入力対象として表示する
- 実践起票は `writingExample` を隠し、`fieldReport.notes` を文章化の材料として表示する
- AI採点は `writingExample` を除外し、`reviewSource` と `scoringRubric` を基準として使用する
- 両モードとも、`templateId` に対応する同じプロジェクトテンプレートを使用する

記載例は唯一の正解ではない。AIレビューの事実源は、観測記録・仕様・証跡から独立して定義した `reviewSource` とする。

`fieldReport.notes` と `reviewSource` は `writingExample` から画面表示時に自動生成しない。現場チャット、追加確認、仕様情報などの断片としてシナリオごとに作成し、利用者が必要な事実を選んで題名と各セクションへ再構成できるようにする。

### 5.2 項目ごとの学習支援

利用者向けには当面2モードだけを表示する。ただし、内部では項目ごとに支援方法を設定できる構造にする。

プロジェクト所定のテンプレートと学習支援は別のデータとして扱う。テンプレートが表示されていること自体を、学習支援または難易度低下とはみなさない。

想定する支援方法：

| 支援方法 | 内容 |
| --- | --- |
| 完成文入力 | 完成文を表示し、そのままタイピングする |
| 書き出し補助 | 文頭や定型表現だけを表示する |
| 要点補助 | 本文に含めるべき事実を箇条書きで表示する |
| 自由作成 | 調査情報だけを基に全文を書く |

実践起票の初期案では、題名と全セクションを「自由作成」とする。ただし、利用者テストで難しすぎると判明した場合は、一部を「要点補助」または「書き出し補助」へ変更できるようにする。

将来の中間レベル例：

| 項目 | 支援方法 |
| --- | --- |
| 題名 | 自由作成 |
| 詳細 | 要点補助 |
| 前提条件 | 完成文入力 |
| 操作手順 | 完成文入力 |
| 期待結果 | 書き出し補助 |
| 備考 | 要点補助 |
| 実際の動作 | 自由作成 |
| 再現性 | 完成文入力 |

現時点では、この中間レベルを利用者向けモードとして公開しない。

## 6. AI採点の基本方針

### 6.1 採点対象

AIは模範回答との文字列一致ではなく、シナリオごとの採点基準に照らして評価する。

6つの評価軸：

1. 事実性
2. 情報充足
3. 再現性
4. 期待結果と実際の動作の分離
5. 解釈の明瞭さ
6. 切り分け支援

### 6.2 採点基準データ

各シナリオは、完成文章だけでなく採点用の基準を持つ。

想定項目：

```js
{
  requiredFacts: {
    subject: [],
    detail: [],
    preconditions: [],
    steps: [],
    expected: [],
    actual: [],
    reproducibility: []
  },
  forbiddenClaims: [],
  optionalFacts: [],
  rubricNotes: []
}
```

`requiredFacts` は、そのまま書くべき文章ではなく、回答に含まれるべき意味を表す。

### 6.3 AIの応答形式

画面へ安定して表示できるように、AIには構造化された結果を返させる。

想定項目：

```js
{
  totalScore: 0,
  dimensions: {
    factualGrounding: 0,
    informationCoverage: 0,
    reproducibility: 0,
    expectedActualSeparation: 0,
    interpretiveClarity: 0,
    investigationReadiness: 0
  },
  verdict: "追加確認を推奨",
  overallAssessment: "",
  readerQuestions: [],
  ambiguityRisks: [],
  investigationAdvice: [],
  rewriteSuggestions: [],
  strengths: []
}
```

点数だけを返す形式にはしない。利用者が次の回答で何を直せばよいか分かることを優先する。

### 6.4 採点の一貫性

AI採点には揺れがあるため、次の対策が必要になる。

- シナリオごとに採点基準を固定する
- AIへ渡す入力形式を固定する
- 点数の根拠を必ず返させる
- 同じ内容を表現だけで過度に減点しない
- 重大な事実誤認と文体上の改善を分ける
- 採点モデルやプロンプトのバージョンを記録する
- 題名、本文、チケット項目、添付、添付説明が同一の修正版はGeminiへ再送せず、前回の点数とフィードバックを再利用する
- 修正版は前回の回答・評価・改善点を比較材料として渡し、前回と同じ品質の評価軸を別基準で採点し直さない
- 前回存在した事実の削除、新しい根拠なしの断定、正しかったチケット項目・添付の悪化がない場合、AIの出力揺れだけによる減点をサーバー側で抑止する
- Gemini 3.xの生成設定では独自のtemperatureを指定せず、回答内容から生成した固定seedを使う

## 7. セキュリティとシステム構成

現在のアプリは静的HTMLとJavaScriptで動作している。

Gemini APIの認証情報をブラウザへ埋め込んではならない。`main.js`、HTML、公開リポジトリ、ブラウザの保存領域へAPIキーを置かない。

AI採点には、ブラウザとGemini APIの間にバックエンドが必要になる。

想定構成：

```text
ブラウザ
  ↓ 回答とシナリオID
採点用バックエンド
  ↓ 採点基準を付加
Gemini API
  ↓ 構造化された採点結果
採点用バックエンド
  ↓ 検証済みの結果
ブラウザ
```

ブラウザから採点基準の正解データをすべて送る方式は、答えの露出や改ざんにつながるため避ける。

## 8. AI採点が失敗した場合

AI採点が利用できない場合でも、入力したチケットを失わないようにする。

必要な動作：

- 入力内容を保持する
- 再採点できる
- 採点失敗と回答不正解を区別して表示する
- タイムアウト時に連続送信しない
- 採点できなくても回答内容を確認できる

## 9. 段階的な開発案

### フェーズ1：実践起票の入力体験

- 題名を自由入力できる
- 固定見出しごとに本文を入力できる
- 入力材料を参照できる
- 回答を送信前に確認できる
- 見本入力の完了後、同じ題材の実践起票へ進める
- 実践起票中は見本回答を表示しない
- AI採点はまだ接続しない

### フェーズ2：シナリオ別採点基準

- 必須事実を定義する
- 禁止する断定を定義する
- 参考回答を定義する
- 既存シナリオ1件で採点基準を試す
- 全シナリオへ固定IDを付与する
- 5種類のテスト回答と期待する点数範囲・指摘を定義する
- 受験履歴と採点結果の保存形式を確定する
- GAS・Sheets・データベースで共通利用する保存インターフェースを確定する
- 固定サンプルを使って採点結果画面を確認する

### フェーズ3A：認証付きGemini採点パイロット

- Google Identity Servicesでログインする
- バックエンドでGoogle IDトークンを検証する
- 検証済みの`sub`を利用者IDとして使用する
- 採点用バックエンドを用意する
- 構造化された採点結果を取得する
- 結果画面へ読み手視点の文章レビューと6軸レーダーを表示する
- エラー時の再試行を用意する
- APIキーをブラウザへ置かない
- 総合点は評価軸の点数からバックエンドで算出する
- 採点基準、プロンプト、モデルのバージョンを保存する

初期パイロットではAI採点APIの不正利用を避けるためGoogleログインを必須とした。利用者テストでログインが実践起票開始の障壁になったため、Firebase匿名認証へ移行する。匿名利用でもAPIキーはサーバーに保持し、利用者・接続元IP・サービス全体の共有上限でAIレビューを保護する。

### フェーズ3B：Sheets保存と履歴・ステータス

- GAS経由でUsers、Attempts、ScoringResultsへ追記する
- 過去の受験と採点結果を表示する
- シナリオごとの習得状態を表示する
- 保存処理を共通インターフェースの背後へ置く

### フェーズ3C：ランキング

- 見本入力と実践起票のランキングを分離する
- 公開用ニックネームとランキング参加設定を用意する

### フェーズ4：難易度調整

- 利用者の回答と誤り方を確認する
- 難しすぎる項目へ要点補助を追加する
- 必要な場合だけ中間モードを公開する

最初から全シナリオへ展開しない。1シナリオで入力体験と採点基準を固めてから増やす。

## 10. 初期対象シナリオの条件

最初の検証には、専門知識が少なく、期待結果と実際の動作が明確なシナリオを選ぶ。

候補：

- 顧客管理システム
- 保存ボタンの連続クリックによる重複登録

このシナリオは、題名、操作手順、期待結果、実際の動作、再現性を明確に分離しやすい。

## 11. 完了条件

### 11.1 フェーズ1

- 見本入力と実践起票を明確に選び分けられる
- 見本入力と実践起票が同じシナリオデータを共有している
- 見本入力の完了後、同じ題材の実践起票へ進める
- 題名を空欄から作成できる
- 固定された各セクションへ文章を入力できる
- 入力材料を見ながら作成できる
- ページ内で回答内容を失わずに確認できる
- 未入力項目を送信前に確認できる
- 見本入力の既存動作を壊さない

### 11.2 フェーズ2

- 全シナリオに重複しない固定IDがある
- 1シナリオの必須事実、禁止する断定、任意事実が定義されている
- 採点基準の評価軸の配点合計が100である
- 5種類のテスト回答に期待点数範囲と期待指摘がある
- 受験履歴と採点結果にスキーマバージョンがある
- 採点結果がGeminiの構造化出力で返せる形になっている
- SheetsからデータベースへIDを変えずに移行できる
- 固定サンプルで採点結果画面を確認できる

### 11.3 フェーズ3

- Google IDトークンをバックエンドで検証できる
- 受験履歴と採点結果をGAS経由で保存できる
- 過去の成績とステータスを本人だけが参照できる
- AI採点結果をセクション別に確認できる
- 採点失敗時も入力内容が保持される
- ランキングへGoogleアカウントの本名・メールアドレスを表示しない

## 12. 未決定事項

## 13. 現時点の推奨判断

- 利用者向け作成モードは「見本入力」と「実践起票」の2つに絞る
- 実践起票では、題名と全セクション本文を自分で作成する
- セクション見出しは最初は固定する
- 内部では項目ごとの支援方法を変更できるようにする
- AI採点は1シナリオだけで品質を確認してから広げる
- 中間モードは必要性が確認されるまで公開しない
